🧠 TO-DO LIST – Sistema de Formularios (SchemaForm + Builders + Hooks)

🩵 Nivel 1 — Refactor técnico inmediato

Objetivo: Reducir duplicación y hacer los formularios más robustos.

  • Centralizar manejo de fallback en SchemaForm

    • Mover toda la lógica isFallback / fallbackMessage al propio SchemaForm.

    • Crear un subcomponente <SkeletonForm /> que renderice los inputs y selects deshabilitados.

    • Evitar que los builders tengan que saber del estado de carga o error.

  • Unificar el isFallback y fallbackMessage como prop del SchemaForm 

    jsx
    <SchemaForm
  values={linea}
  fields={fields}
  isFallback={loading || error}
  fallbackMessage={error ? "⚠️ Error al conectar" : "⏳ Cargando..."}
/>

  • Refactorizar buildOrdenServicioFields y otros builders

    • Eliminar lógica de fallback interna.

    • Solo definir estructura de campos, sin preocuparse por estados externos.

💚 Nivel 2 — UX / Usabilidad

Objetivo: Mejorar la experiencia del usuario y percepción de carga.

  • Agregar un sistema de retry (reintentar carga)

    • En caso de error, mostrar un botón 🔄 Reintentar.

    • useTiposTrabajo debe exponer un método refetch().

  • Permitir edición parcial en modo fallback (optimistic UI)

    • Campos dependientes del backend → deshabilitados.

    • Campos locales (descripcion, observaciones, etc.) → editables.

  • Soporte visual para fallback

    • Crear un componente tipo FallbackPanel o SkeletonForm.

    • Mostrar icono (⏳ o ⚠️), mensaje y fondo diferenciado.

    • Usar tonos distintos según tipo (info, error, warning).

  • Unificar estilos visuales mediante un theme global

    • Definir constantes de color y tipografía: 

      js
      const FALLBACK_THEMES = {
  loading: { color: '#888', bg: '#f9f9f9' },
  error: { color: '#c0392b', bg: '#fff4f4' },
};

    • Aplicarlos automáticamente según el estado.

🧩 Nivel 3 — Performance y resiliencia

Objetivo: Mejorar la eficiencia y reducir dependencias del backend.

  • Agregar cache local al hook useTiposTrabajo

    • Usar sessionStorage o un pequeño contexto global.

    • Evitar recargar los tipos en cada montaje.

  • Implementar un modo offline/demo

    • Detectar import.meta.env.MODE === 'demo'.

    • Cargar mocks (MOCK_TIPOS_TRABAJO) automáticamente.

    • Desactivar llamadas reales al backend.

📘 Nivel 4 — Documentación y developer experience

Objetivo: Estandarizar el uso del sistema para nuevos formularios.

  • Crear una “guía rápida” (manual interno)

    • Explicar cómo crear un nuevo builder.

    • Cómo pasar isFallback / fallbackMessage.

    • Qué hacer en estados loading y error.

    • Ejemplos prácticos.

  • Agregar un checklist para nuevos formularios dinámicos 

    diff
    ✅ Checklist de nuevo formulario:
- [ ] Hook de datos: useClientes / useEquipos / useTiposTrabajo
- [ ] Props: isFallback + fallbackMessage
- [ ] Campos deshabilitados en fallback
- [ ] Validar los tres estados: normal / loading / error
- [ ] Botones desactivados si isFallback

  • Documentar visualmente los estados

    • Capturas o storybook de cómo se ve cada modo (normal, loading, error).

    • Facilita QA y testing.

💎 Nivel 5 — Avanzado (opcional / a futuro)

Objetivo: Alcanzar una arquitectura profesional tipo “form engine”.

  • Integrar SWR o React Query para los hooks de datos

    • Control automático de cache, refetch y estados de error.

    • Simplifica useTiposTrabajo.

  • Soporte para validaciones diferidas o dependientes

    • Ejemplo: si el usuario selecciona un tipo, precargar precio base automáticamente.

    • Reducir fricción y aumentar productividad.

  • Animaciones suaves en estados de carga / cambio

    • Transiciones CSS en SchemaForm o Skeletons.

    • Mejora la percepción visual de fluidez.
